`lucos_worlds` (BookStack-adopted, `theme/lucos/public/css/custom.css`) removed its dark-mode toggle in #61/#75 — `.dark-mode` is unreachable through the UI, only via a hand-crafted `PATCH /preferences/toggle-dark-mode` (accepted as out of scope for a single-user private system). Several theme rules were then simplified from paired `:not(.dark-mode)`/`.dark-mode` selectors to a single bare selector, on the reasoning that the dark-mode branch "can now never match."

**That reachability reasoning is correct, but a bare selector does not reliably render correctly if `.dark-mode` is ever forced onto `<html>` anyway** (e.g. by that residual PATCH route). BookStack's own compiled CSS defines many of its own overrides as `html.dark-mode <selector>` — a compound selector combining the `html` type selector with the `.dark-mode` class — which has *higher* specificity than a bare `:root`/`body`/`.class` selector, and specificity beats source order regardless of which `<link>` loads last. Confirmed instances: `html.dark-mode {background-color:#111}`, `html.dark-mode body{color:#aaa}`, `html.dark-mode .card{background-color:#222}`. There is also a THIRD source, invisible to any static CSS read: BookStack renders its own `:root`/`:root.dark-mode` custom-property block (`--color-primary` etc.) inline in every page's `<head>` via `layouts/parts/custom-styles.blade.php` — not in the compiled stylesheet at all.

**Fix pattern (established in #79, applied estate-wide in #80/#81):** pair the bare selector with an explicit `:root.dark-mode`-scoped equivalent, e.g. `:root, :root.dark-mode { ... }` or `.content-wrap.card, :root.dark-mode .content-wrap.card { ... }`. `:root.dark-mode` (pseudo-class + class = weight 2 in the specificity "class" column) reliably beats BookStack's `html.dark-mode X` (type + class = weight 1 in that column plus a type-selector) because CSS specificity compares column-by-column, and matching or exceeding the class-count column wins outright regardless of the type-selector column. Not every bare selector in this file is actually affected — verify each one individually (see [[feedback_verify_css_on_running_instance]] for the CSS-OM method); as of #80/#81, `.page-content h1::after`/`.page-content h2::after` (heading rule) and `.page-content a` (link underline) were checked and confirmed to have no competing BookStack dark-mode rule at all, so they're correctly left as bare selectors.

If this file is touched again and a claim needs "is this rule genuinely unconditional under `.dark-mode`" verified, don't re-derive from scratch — the method and the known-affected/known-clean list above should still be current as of 2026-08-07 (repo history: #61→#75→#63→#70→#69→#76→#79→#80→#81, all same evening).
