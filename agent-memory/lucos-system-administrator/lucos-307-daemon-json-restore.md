lucas42/lucos#307 (Needs Analysis, owned by sysadmin): avalon's rebuilt `/etc/docker/daemon.json` (mtime 2026-09-15 22:28, i.e. lucas42's own Step 1 provisioning window) is missing `registry-mirrors: ["https://docker.l42.eu"]` (lucos#106) and `live-restore: true` (lucos#107). Confirmed not deliberate — no record of a decision anywhere (runbook #296 explicitly listed both for restoration; incident report doesn't mention them); matches the same "unrecorded hand-edit during rebuild" pattern as the `DNS=8.8.8.8` divergence found the same day (lucas42/lucos_media_seinn#639).

**Confirmed via Docker's own docs (2026-09-27): both settings are hot-reloadable via `systemctl reload docker` (SIGHUP), including the disabled→enabled transition for live-restore itself — no restart needed, zero container impact.** This generalizes [[docker-daemon-restart-risk]] beyond "many options are reloadable" to a verified-against-source confirmation for these two specifically. Reusable fact for any future daemon.json change on production hosts: always check the live-restore/reload docs before assuming a restart is needed.

Full analysis + exact command block (backup, edit, validate JSON, reload, verify via `docker info` + before/after `docker ps` diff) posted at https://github.com/lucas42/lucos/issues/307#issuecomment-5860583841. Target config matches the pre-rebuild rescued daemon.json exactly (verified by extracting `avalon-host-config.rescue-2026-09-14.tar.gz` on xwing) — plain `https://docker.l42.eu` mirror URL, not the untested `localhost:8038` alternative #106 speculated about (mirror confirmed healthy/reachable from avalon itself).

**APPLIED 2026-09-28** (lucas42, 16:29:43Z 2026-09-27); my first verification pass was WRONG on check 3 and got corrected by SRE — reopened, see below. Checks 1/2 stand:
- Checks 1 & 2 (settings live in `docker info`/daemon.json; no container restarted from the reload) were based on direct evidence — `systemctl show docker --property=ActiveEnterTimestamp,NRestarts` for daemon-process continuity (unchanged since rebuild boot, `NRestarts=0`, proves dockerd itself never restarted) plus per-container `StartedAt` timestamps. This technique is sound and worth reusing.
- **Check 3 ("pulls go through the mirror") was a FALSE POSITIVE — do not repeat this mistake.** I test-pulled `hello-world` (fully public, unauthenticated) and saw dockerd's requests hit `docker.l42.eu` in `lucos_router`'s access log, and called that confirmation. It wasn't: dockerd transparently falls back to Docker Hub when a mirror errors, so a successful pull with requests visible in the router log looks *identical* whether the mirror actually served the layers or errored and fell through. lucos-site-reliability found the mirror was actually returning 401 for `hello-world` (and `pgvector/pgvector`, `lucos_photos_api` blobs) the whole time — auth passthrough to Docker Hub was broken, which then broke the `photos.l42.eu` hotfix deploy pulling `pgvector/pgvector:pg16` ("no basic auth credentials"). **A public image can never test the auth-passthrough path** — the actual failure mode. To verify a registry mirror is really serving (not just receiving and falling through), check the mirror's *own* response code/behaviour for the pulled layers, not just that dockerd's requests reached it. Corrected and reopened: https://github.com/lucas42/lucos/issues/307#issuecomment-5874781873. SRE owns the resulting incident — do not touch avalon/the mirror unless asked.

**Root cause found (read-only investigation, 2026-09-28, shared with SRE — not filed/fixed by me, theirs to action):** `lucos_docker_mirror_web` (nginx) gates every `/v2/` request with HTTP Basic Auth (`auth_basic`/`.htpasswd`) before it reaches the `registry` backend (confirmed: registry's own container log shows zero entries for the failing requests — nginx rejects them first). Comparing nginx's access log for succeeding vs failing pulls in the same few-minute window: CircleCI's BuildKit (`lucos-ci` stored creds) gets 401→retry-with-creds→200 (normal challenge/response). Avalon's own dockerd, doing the deploy-time `docker compose pull`, gets a bare 401 with no retry — it has no stored credential for `docker.l42.eu` to answer the challenge with. This is a *different* credential than anything in `daemon.json` (`registry-mirrors` has no auth field) — mirror-auth for dockerd itself normally lives in `/root/.docker/config.json` (a `docker login docker.l42.eu` artifact), which the rescued `avalon-host-config.rescue-2026-09-14.tar.gz` never captured (checked: no `.docker/config.json` anywhere in it). Same "lost in the rebuild, outside what Step 1/any runbook restored" shape as the SSH host keys, daemon.json settings, and DNS resolver config. Unverified (needs root): whether `/root/.docker/config.json` is actually empty on avalon, and whether xwing/salvare have a working one to compare against.
