Read `lucos_deploy_orb` source directly (`src/commands/deploy.yml`, `src/commands/fetch-publish-creds.yaml`, `src/jobs/build.yml`) rather than assume from `docker-conventions.md` — the doc doesn't cover this.

**Two separate, unrelated fetches from `creds.l42.eu:2202`, both required for a normal CI run:**
1. **Deploy-side**: `deploy.yml`'s "Fetch production envfile" step — `scp docker-deploy@creds.l42.eu:$CIRCLE_PROJECT_REPONAME/production/.env`. Has a documented bypass: if the CircleCI project env var `LUCOS_DEPLOY_ENV_BASE64` is set, this step (and the corresponding `ssh-keyscan` of creds.l42.eu) is skipped entirely, decoding the pre-supplied value instead. Currently **only `lucos_creds` itself** has this var set (verified via `GET /api/v2/project/{slug}/envvar` across `lucos_configy`/`lucos_dns`/`lucos_router`/`lucos_firewall`/`lucos_creds` — only the last has it) — it exists specifically to solve lucos_creds's own chicken-and-egg bootstrap.
2. **Build-side**: `fetch-publish-creds.yaml` (used by every `lucos/build` job to get Docker registry push credentials) — unconditional `ssh-keyscan -p 2202 -H creds.l42.eu` then `scp .../lucos_deploy_orb/publish/.env`. **No bypass mechanism at all.**

**Implication:** if `creds.l42.eu` (avalon) is down, NO project can complete a fresh **build**, regardless of service choice — the build-side fetch has no escape hatch. A service can still be **deployed** without a fresh build by reusing an already-published image: find a pre-outage successful pipeline for that service, then `POST /api/v2/workflow/{id}/rerun` with `{"jobs": ["<deploy-job-id>"]}` to selectively rerun only the deploy job (CircleCI treats the earlier `test`/`build` jobs in that workflow as already-satisfied, no re-execution). Combine with a temporary `LUCOS_DEPLOY_ENV_BASE64` project env var (placeholder, non-secret `.env` — just enough for `PORT` validation and whatever the app needs) to also bypass the deploy-side fetch, then delete the env var immediately after.

**Consequence for any avalon-style host rebuild:** a documented CI redeploy priority order that puts anything before `lucos_creds` (e.g. lucos#296's original "`lucos_configy` → `lucos_dns` → `lucos_creds` → …") is wrong in practice — nothing can deploy normally (build+deploy from a fresh commit) until `lucos_creds` itself is reachable at `creds.l42.eu`. `lucos_creds` bootstrapping first, via its own `LUCOS_DEPLOY_ENV_BASE64`, is the only path that doesn't need a workaround — but bringing it up before its data volume is restored mints a fresh `data_key`/`server_key` (see [[configy-undeployed-system-entry-pattern]]-style caution: verify statefulness before the first deploy on a rebuilt host).

**Good test-deploy candidate when picking a "prove the pipeline works" service** (used successfully on lucos#296, 2026-09-16): pick something with no persistent volume and no secret-bearing env vars — `lucos_root` (the l42.eu landing page: `SYSTEM`, `PORT`, `APP_ORIGIN` unused, `LOGANNE_ENDPOINT`, nothing secret) fit well. Avoid anything binding a raw public port directly (DNS 53, mail 25, MQTT 8883) — those go live to the real internet the instant the container starts, regardless of whether DNS/router steps have happened yet.

**Unrelated but hit along the way**: this sandbox's `~/.ssh/known_hosts` had pre-existing corruption (several blocks of "invalid line" entries, likely from concurrent appends across sessions/agents with no locking) that made `ssh-keygen -R <host>` refuse to write back ("Not replacing existing known_hosts file because of errors"). Workaround: run a fresh `ssh-keyscan` to an isolated temp file and pass it via `-o UserKnownHostsFile=<temp>` for the connection, rather than trying to fix the shared file. Didn't attempt to repair the shared file itself — out of scope for the task at hand, but worth knowing before assuming `ssh-keygen -R` succeeded just because it exited 0-looking.
