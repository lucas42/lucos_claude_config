lucas42/lucos#273 (open, awaiting lucas42/architect decision) asks which layer should guard against auto-merged pre-release/breaking base-image bumps, after three production incidents: lucos_mail (alpine, stable bump, 2026-06-11), lucos_contacts/lucos_eolas (python pre-release, caught by CI, no outage, 2026-06-23), lucos_media_metadata_manager (php alpha, ~6.5h outage, 2026-07-31 — incident report PR lucas42/lucos#274).

Four repo-local defences exist, no estate convention: media_import (dependabot `ignore`), mail (CI stack-start check, lucos_mail#61), eolas (`FROM app AS test` — tests run in the shipped image), media_metadata_manager (CI grep rejecting alpha/beta/rc tags, #386).

**I verified (2026-07-31) that the media_import ignore rule actually works**, resolving its own comment's hedge ("if this fails silently, fall back to..."): Dockerfile pins `FROM python:3.14` (floating); Docker Hub has had live 3.15 pre-release tags (`3.15.0b3`/`3.15.0b4`/`3.15-rc`) since 2026-07-16; zero Dependabot PRs for `python` opened on that repo since the rule was added 2026-06-11 (daily schedule, ~40 day window). Checked via Docker Hub registry API + repo's PR history, not inferred.

**Why this matters for #273's "which layer" question:** a working ignore rule is silent in both the success and failure case — nothing would have told anyone if Docker Hub's tag format shifted and the wildcard stopped matching. I only confirmed it works by manually checking Docker Hub. This is a concrete point in favour of the CI-assertion / test-in-shipped-image approaches (visible failure = real signal) over dependabot-ignore, even where the ignore syntax happens to be correct today.

**How to apply:** if #273 lands on a decision, don't re-litigate whether media_import's ignore rule "actually holds up" — it's confirmed as of 2026-07-31. The open question is whether silent-suppression is an acceptable trade-off vs a visible-failure guard, not whether the syntax works.

**Update (2026-07-31, from lucos-site-reliability):** report + #273 corrected to say the ignore rule works, and the framing promoted to a general principle: prefer a guard that fails loudly over one that succeeds silently. Operational consequence: expect `lucos_media_metadata_manager`'s `stale-dependabot-prs` check to go red ~48h after the php alpha bump re-proposes (the new CI guard from #386 rejects it visibly) — that red is *correct*, not an incident; close the PR, don't debug the CI job. See `ops-checks.md` Known Limitations for the ops-check-facing version of this note. Tradeoff noted both ways: the ignore layer produces zero stale-PR noise (a real cost of the CI-guard approach), while the CI-guard layer produces visible, correct-but-noisy red statuses (a real cost of that approach) — SRE left this unweighted in #273.

**Update (2026-08-02, architect's final recommendation on #273):** frame rejected ("block pre-releases" was never the real question) and replaced with an ordered recommendation: (1) `/_info` `checks` must include a self-function check, not just dependency checks — ADR-worthy, architect will write it; (2) CI boots the shipped image and asserts `/_info` healthy, *only meaningful after (1)*; (3) non-HTTP services get a narrower "does it start and stay up" form; (4) a CI assertion rejecting pre-release base tags, framed as "a pre-release base image requires a human decision" (explicit opt-in), not a blanket ban — kept for intent/vuln-management reasons, not because it would've caught the mail incident (it wouldn't). **Layer choice for (4) explicitly favours CI-assertion over dependabot `ignore`**, on an automatability argument: a stale PR is discoverable/sweepable, a silently-over-matching `ignore` rule is not (nothing in the system would know a suppressed update ever existed). Dependabot supersession-while-red is a named known-unknown (never observed) but made non-load-bearing: closing a blocked pre-release PR doesn't suppress the dependency, Dependabot just re-raises on the next version — verified via the "OK, I won't notify you again about this release..." reply on both lucos_eolas#311 and lucos_contacts#741. Residue cost of the CI layer corrected twice, settled at: **at most one open failing PR per repo per dependency group**, self-clearing when stable lands (org-wide: 77 confirmed supersession instances, zero open Dependabot PRs org-wide as of 2026-08-02). Status as of that comment: **Awaiting Decision, Owner lucas42, Priority High** — analysis complete, nothing further pending from architecture/reliability/security/sysadmin. Not yet decided.

**Update (2026-08-06/07, correction):** the predicted `stale-dependabot-prs` red for `lucos_media_metadata_manager` never arrived (2 daily Dependabot runs passed, zero open Dependabot PRs org-wide). Cause unconfirmed — logged as a footnote, not decision-grade — but if anything it means the CI-layer residue is *lower* than the figure #273 settled on, not higher. Doesn't reopen the layer comparison.

**Update (2026-08-08): fourth occurrence, on `lucos_creds`.** Dependabot proposed `python:3.14.5-alpine3.22 → 3.15.0b2-alpine3.22` on `configy_sync` (lucos_creds#511, closed by code-reviewer pre-merge) — **the exact same upstream pre-release** (`3.15.0b2`) that broke lucos_contacts#741/lucos_eolas#311. `lucos-issue-manager` filed lucos_creds#512 asking for a repo-local `ignore:` fix; I posted a guard-and-scope assessment there (https://github.com/lucas42/lucos_creds/issues/512#issuecomment-5225968745) recommending **against** implementing it — it's the layer #273 already leans away from, and it would be a fifth parallel per-repo mechanism when #273 explicitly wants convergence. Also added the occurrence as a fourth data point on #273 itself (https://github.com/lucas42/lucos/issues/273#issuecomment-5225969419). **How to apply going forward:** don't let individual per-repo pre-release Dependabot tickets turn into bespoke fixes — they're all instances of #273's still-open decision; point them at it and recommend waiting for the staged rollout once lucas42 decides. `lucos_creds` (credential store) is now on record as a blast-radius data point for whenever the rollout ordering gets decided.

**Update (2026-08-08, team-lead's board call on #512):** assessment adopted in full — board set to **Blocked on lucas42/lucos#273** (not Closed, not left as standalone Ready), Owner stays lucos-system-administrator, Priority Low. Team-lead's reasoning, worth reusing as a general pattern: when a ticket's correct resolution is contingent on an unresolved upstream/estate decision, **Blocked keeps the residue visible if the eventual decision doesn't end up covering this case; Closed would assert a prediction about a decision nobody has made yet.** Picked up again on whatever sweep clears blocked-on-X tickets once #273 resolves. Also rewrote #512's body to retain the rejected `ignore:` approach under an explicit "NOT chosen" heading with the reasoning above it, rather than deleting it — an under-specified ticket reading as actionable to a future implementer is a worse failure mode than one that looks unfinished.
