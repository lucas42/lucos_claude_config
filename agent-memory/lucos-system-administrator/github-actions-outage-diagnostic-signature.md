**Symptom signature of a GitHub-wide Actions platform incident** (confirmed 2026-08-06, incident qcvjkzcs7j74, lucas42/lucos_creds#472/#484): a workflow run stays `status: queued` for ~15 minutes with no runner ever assigned, then the job resolves to `conclusion: cancelled` with an **empty `steps` array** (no step ever started). Fetching the raw log for that job returns `BlobNotFound` from GitHub's log storage (404) — itself part of the same incident, not a separate problem. Always cross-check `https://www.githubstatus.com/api/v2/incidents/unresolved.json` before treating this as a repo-specific CI break — a `critical`/`investigating` Actions incident there is conclusive.

**Useful cross-check to confirm it's Actions-specific, not estate-wide**: if CircleCI-driven required checks (`ci/circleci: test`, `ci/circleci: build`) complete normally in the same time window that GitHub Actions jobs (CodeQL, custom workflows) are stalling/getting cancelled, that's a clean signature isolating the outage to Actions specifically — CircleCI is a separate platform unaffected by a GitHub Actions incident.

**A cancelled run does not self-heal.** Once `status: completed` / `conclusion: cancelled`, it stays that way forever — the only fix is a fresh re-run (`POST .../actions/runs/{id}/rerun-failed-jobs`) once the platform incident clears. Don't watch the stuck run itself expecting it to resolve; watch the incident status instead, then manually re-trigger.

**Branch protection quirk — CircleCI checks don't appear in check-runs, only commit-statuses.** `GET /branches/{branch}/protection/required_status_checks` lists the required context *names* (e.g. `ci/circleci: test`), but to see whether they're actually green, query `GET /commits/{sha}/status` (combined status API) for CircleCI-sourced contexts — they report via the legacy commit-statuses mechanism, not the newer check-runs API used by GitHub Actions / CodeQL. Querying only check-runs will make it look like CircleCI's required checks are simply absent, when they're just reporting through a different endpoint. Don't infer "not required" or "missing" from an empty check-runs list alone — read `required_status_checks.contexts` directly (available to any App with `administration:read`/`write`, no need to infer merge-blocking status from `mergeable_state: unstable` vs `blocked`).

**`workflow_dispatch` posts a check-run on the target SHA during a webhook-throttled (but job-execution-recovered) Actions outage — but does NOT reliably satisfy the PR merge gate. Confirmed 2026-08-06, lucos_worlds#66/#72, via my own GraphQL query after two conflicting secondhand reports (see below).** GitHub's status updates can split an incident into two independent halves: job *execution* success rate recovering (e.g. to 97%) while webhook *delivery* stays throttled — `push`/`pull_request` events then silently fail to trigger new runs (confirmed: a direct `git push` merge produced zero CodeQL runs during the window). `workflow_dispatch` is a direct API call, not a webhook-delivered event, so the run itself executes and posts a check-run via `GET /commits/{sha}/check-runs` — but **that REST endpoint is not what the merge gate reads.** The gate reads the GraphQL `pullRequest.mergeStateStatus` + `commit.statusCheckRollup.contexts`, and on #72 the *required* context (`Analyze (python)`, per `required_status_checks.contexts` in branch protection) never appeared in that rollup — only a differently-named `CodeQL` check-run (a separate, non-required GitHub-Advanced-Security context) and the CircleCI contexts did. Net effect: `Analyze (python)` showed `completed`/`success` via REST check-runs while the PR stayed `mergeStateStatus: BLOCKED` via GraphQL — a real, reproduced gap, not resolved by waiting.

**Verify via GraphQL, not REST, before concluding a dispatch unblocked a PR:**
```
gh-as-agent --app <persona> graphql --input query.json
# query: repository(...) { pullRequest(number: N) { mergeable mergeStateStatus reviewDecision
#   commits(last: 1) { nodes { commit { statusCheckRollup { state contexts(first: 20) { nodes {
#   __typename ... on CheckRun { name conclusion status } ... on StatusContext { context state } } } } } } } } }
```
Cross-check the required context *names* from `GET /branches/main/protection/required_status_checks` — a check-run can post under a different name (`CodeQL` vs the required `Analyze (python)`) and look like it satisfied the gate via REST when the rollup shows otherwise.

**This flip-flopped twice before landing — a caution on relaying teammates' verification claims.** First pass: I called it confirmed based on REST check-runs alone (wrong endpoint). Second pass: a teammate reported GraphQL rollup `SUCCESS`/`mergeable: MERGEABLE` and called the gap disconfirmed (their `mergeable` field check was real but doesn't reflect required-check gating — `mergeStateStatus` does, and wasn't checked). Third pass: another teammate re-checked and found `mergeStateStatus: BLOCKED` with the required context absent from the rollup — I reproduced that independently myself before updating this memory. Moral: "confirmed via GraphQL" is not itself sufficient provenance — check *which field* was read.
