Three corrections in one session (2026-07-14, `lucos_agent_coding_sandbox#95`/`#98`/`#99`), each caught by team-lead, each the same underlying shape with a different surface:

1. **Generalising verified command output to an unverified host** — wrote "verified on avalon, xwing, salvare" when only xwing/salvare's `sudo -n -l` output was actually captured; avalon had only been tested with a different (blanket) check. Fix: [[agent-sudo-scope]] — "verified on {hosts}" needs per-host captured output, no exceptions for siblings on the same playbook.
2. **Inferring an unprobeable environmental fact from plausibility** — "remote-only Pis have no console" sounded reasonable and was wrong (per lucas42: xwing/salvare are physically accessible, avalon is not). Fix: `references/ssh-production.md`'s environmental-facts rule — physical accessibility, hardware topology, hosting arrangement can't be verified by re-running a command; source from lucas42 or mark explicitly unknown.
3. **Dropping a teammate's explicit hedge while paraphrasing** — team-lead reported "confirmed the upgrades happened, NOT verified no incident resulted"; my paraphrase into a runbook comment read "...with no incident," asserting exactly what they'd flagged as unverified. Fix: `references/teammate-quote-verification.md` now names this failure mode directly — a hedge is part of the claim, and compressing it out during paraphrase (not misquoting, which `verify-teammate-quote` would catch) produces the same downstream harm.

**Why this kept recurring in one session:** each individual fix (verify per-host, don't infer environmental facts, preserve hedges) addresses a different *surface*, but the underlying failure is the same — writing something down with more confidence than the evidence actually supports, because the unsupported version reads more cleanly or fits the narrative being built. Team-lead's framing: good underlying work each time, the inference was the weak link every time.

**How to apply:** before any comment/issue-body/memory sentence that states a fact rather than describes an observation, ask "did I personally see this, for this specific subject (host/claim/hedge), in this session" — not "does this sound right given what I know." If the answer is no, either go verify it (per-host command, direct question to lucas42) or write the uncertainty down explicitly rather than smoothing it into an assertion. This applies with *extra* force when relaying someone else's finding — their hedge is data, not friction to edit out.

**Coda, same day:** declining to carry forward team-lead's "~8" figure (point 3 above) without verifying it myself turned out to matter more than expected — the real count was 27; their "~8" was an artifact of a `head -8` on their own grep, i.e. they'd counted the rows they'd printed, not the rows that existed. Generalisable lesson, applies to my own `grep`/`head`/`tail`-piped counts during ops checks and investigations, not just to relayed numbers: **a count produced by a truncated command is an artifact of the command, not a measurement, and it carries false precision precisely because it looks like real data.** Before stating any number derived from piped shell output, check whether a `head`/`tail`/`| sort | head` sits between the raw count and what got displayed — `grep -c` (unbounded) is safe; `grep ... | head -N` is not a count of anything.

5. **Generalising a verified negative (absence) from one search term to an unverified related one** (2026-08-09, lucos_router#104, caught by team-lead). Grepped `nas.l42.eu|aurora` against `lucos_configy/config/systems.yaml` — correctly confirmed absent — and separately skimmed the first ~60 (alphabetical) lines of the same file. Then asserted "neither `tfluke.uk` nor `nas.l42.eu` exists in configy" as a single claim, without ever actually grepping `tfluke`. It did exist — as `tfluke`, domain `app.tfluke.uk` — just under a different hostname than the one hardcoded in `lucos_router`'s script (which routes `tfluke.uk`/`www.tfluke.uk`, the apex/www, not `app.tfluke.uk`). Confirmed this specific case was NOT a stale-checkout problem — local working tree and `origin/main` agreed on the `tfluke` entry; the gap was search scope, not staleness. The load-bearing error was building an argument ("these domains aren't lucos systems, hence can't be in configy") on top of the unverified half of a two-item claim — the real shared property (backend isn't a local port on the host) was different and weaker as a categorical argument. Fix now in the persona file's investigative-discipline section: a negative claim about multiple items needs each item searched by its own name, not inferred from an adjacent verified search.

6. **Naming a root cause from commit-log timing without reading the deployed artifact** (2026-08-17, lucos_backups#390, caught by lucos-site-reliability during incident-report drafting). Filed the crash-loop issue blaming PR #389 (a `charset-normalizer` Pipfile.lock bump merged shortly before the crash began) and proposed reverting it — a reasonable read of "recent change touched the exact broken package," but wrong. SRE's investigation read the lockfile *inside the built image* and found it still pinned the old version; the actual installed package was newer, because the Dockerfile's `RUN pipenv install` re-resolves at build time and ignores the lock entirely. The real trigger was an unrelated commit (a `github/codeql-action` bump) that merely caused a rebuild, which then picked up a fresh transitive dependency on its own. "A recent change touched a related area" was the whole basis for the claim — exactly the trap named in `references/incident-reporting.md`'s "Verify the root cause actually caused *this* failure" section. Fix: for any root-cause claim about *what's actually running*, check the built artifact (installed package versions, lockfile as shipped) before the commit log — the log tells you what was authored, not what got deployed. See `references/docker-conventions.md`'s "Reproducible builds" section for the general Dockerfile pattern this exposes.

4. **Reporting our own wrapper's version tag as if it were the third-party upstream app's version** (2026-07-30, lucos_worlds/BookStack, caught by lucos-architect) — I ran `docker ps` on avalon, saw `lucas42/lucos_worlds_web:1.2.4`, and told the architect "the deployed BookStack image tag is 1.2.4" — stated as an observed fact. `1.2.4` is our wrapper repo's own semver (bumped on any commit to `lucos_worlds`, via `VERSION` build arg per lucas42/lucos_worlds#25), not BookStack's version (BookStack uses date-based tags like `v26.05.2`, from `/app/www/version` inside the container). The numbers happened to be mutually consistent this time (BookStack really was `v26.05.2`, matching the Dockerfile pin) — but that was luck, not evidence; a wrapper rebuild for an unrelated commit bumps `1.2.x` without touching BookStack's version at all, so the same command could just as easily have "confirmed" a stale upstream version. See [[lucos-worlds-bookstack-deploy]] for the general rule this produced: **for any wrapped/vendored third-party app, our own image tag tells you which of our builds is running and nothing about which upstream version is inside it — check the upstream app's own version file/API, not our tag, whenever the claim is about the upstream app specifically** (e.g. a security-patch verification like lucas42/lucos_worlds#55, where "the wrapper tag bumped" is not evidence the CVE fix is live).
