**lucos_deploy_orb#192** (2026-08-19, analysis posted, recommended Ready): a failed deploy today leaves the service DOWN — `docker compose up` recreates the container before discovering the healthcheck fails, and the previous working container is already gone. Root incident: `lucos/docs/incidents/2026-08-17-backups-python-alpha-charset-normalizer.md` (15h24m outage).

**Key design insight, evidenced by the actual incident data — don't derive a rollback target from git tags, even "second-newest tag."** The 2026-08-17 tag sequence was v1.4.31 (last known-good) → v1.4.32 (broken) → v1.4.33 (broken, same defect). Asked from v1.4.33's perspective, "previous tag" resolves to v1.4.32 — itself broken. The correct signal is "the image that was actually running and healthy immediately before this deploy attempt," captured via `docker inspect --format '{{.Config.Image}}'` on the currently-running (or stopped-not-removed, for host-net services) container **before** `docker compose up` touches anything — not inferred from tag ordering.

**Fix belongs in the orb, not per-service compose.** `src/commands/deploy.yml`'s deploy step is shared by every `deploy-{avalon,xwing,salvare,virgon-express}.yml` job across all ~55 systems; repos pin the orb as a floating `lucos/deploy@0`, so an orb fix ships estate-wide with zero per-repo PRs. Compose files already conform to the `${VERSION:-latest}` templating this depends on — nothing about them needs to change.

**Separate, independent, cheaper bug in the same file:** "Determine deployed version from git tags" (`deploy.yml`) does `git tag --list 'v*' --sort=-v:refname | head -1` — globally newest tag, ignoring which commit is checked out. Breaks specifically when re-running an *old* CircleCI pipeline as an emergency rollback lever (the incident's attempted recovery — deployed v1.4.33, the broken version, instead of the old pipeline's own v1.4.31). Fix: `git tag --list 'v*' --points-at HEAD --sort=-v:refname | head -1`. Recommended as its own ticket rather than bundling with the rollback feature.

**Explicitly out of scope:** Option 2 (health-gated blue-green cutover — start new container alongside, swap on healthy) needs a second-container-plus-repoint mechanism at the `lucos_router` layer and per-service compose changes across the estate — a much bigger architectural change than a bounded retry-loop extension. Agreed with SRE's own ticket framing that it isn't worth it now; would need its own ADR if ever revisited.

**Auto-rollback must stay loud, not quiet.** Job must still `exit 1` even after a successful rollback (preserves "this version was broken" signal — must never turn the pipeline green). And it needs a distinct Loganne event on rollback, separate from the normal deploy-log event — this incident's own Stage 5/6 findings (`lucos_docker_health`'s 42 false "recoveries" during an outage that never recovered, and "detection worked, response didn't") are specifically about quiet self-healing being worse than staying visibly broken, because it removes the reason to look.

See [[configy-undeployed-system-entry-pattern]] for a similarly evidence-driven design constraint (read the actual source/data before proposing the fix, not just the surface description).

**Implementation (2026-08-28, PR lucas42/lucos_deploy_orb#194):** built as a new `deploy-compose` command (capture → stop-host-net → retry-with-rollback), invoked from `deploy.yml`. It never exits non-zero itself — exports `DEPLOY_SUCCEEDED`/`ROLLBACK_ATTEMPTED`/`ROLLBACK_STATUS`/`ROLLED_BACK_TO_VERSION` to `$BASH_ENV`, and the caller fails the job in a final step. This is what let it be tested for real against a local Docker daemon in CI (no SSH/live host needed) — CircleCI orb command-invoking-command works fine (confirmed via `circleci config validate` on the packed+inlined orb before ever pushing). **Local dry-run against real Docker before pushing (bootstrap a healthy image, deploy an always-unhealthy one, watch it actually roll back) caught nothing new but confirmed the mechanism end-to-end** — worth doing for any change to this orb given its ~55-repo blast radius.

**Bug caught by code-reviewer's first pass, real and live-reproducible:** the initial `PREV_VERSION` derivation took `head -1` of the captured-images file — i.e. whichever service `docker compose config --services` listed first, not necessarily the `${VERSION}`-templated one. `lucos_locations` has exactly this shape (`otrecorder`: fixed `image: owntracks/recorder`, no healthcheck, declared before the templated `otfrontend`/`mqtt`) — a fixed-image, healthcheck-less sidecar passes the "valid rollback target" gate and would get picked, producing an invalid image reference and a failed rollback. **Fix: identify version-driven services via the same `yq` image-pattern-match technique already used for host-net detection**, and derive `PREV_VERSION` only from those. Added a regression test (`test-deploy-compose-rollback-multi-service`) reproducing the exact `lucos_locations` shape (sidecar declared before app) to lock it in.

**Gotcha: `<<<` (bash here-string) breaks CircleCI orb YAML** — collides with `<< parameters.x >>` template interpolation syntax, fails at `circleci config validate`/pack time with "Expected valid identifier". Use a file + `while read ... done < file` instead (matches the existing `rollback-targets.env` pattern in this same file) — never a bash here-string or process substitution starting with `<` in orb command YAML.

**Local validation trick for orb changes**: `circleci config pack src > packed.yml`, then strip everything except `commands`/`jobs`/`executors` (top-level `description`/`display` aren't valid in an inline-orb embed), indent 4 spaces, and substitute for `deploy: lucos/deploy@dev:alpha` in a copy of the consuming config (`test-deploy.yml`) — `circleci config validate` on the result catches command-name typos, bad parameter refs, and forbidden bash syntax before ever pushing. No CircleCI API token needed for `config pack`/`config validate` (only `orb validate` needs auth). Installed via the official install script + `sudo -n`; matches CircleCI's actual `yq` (mikefarah/yq v4, Go) — the Debian-apt `yq` package is a different tool (kislyuk's Python jq-wrapper) with different quoting/output behaviour, don't trust it for orb testing.

**REJECTED by lucas42, 2026-08-28T21:37Z: closed PR #194 unmerged, issue #192 closed `not_planned`.** His comment in full: "No.  This is adds much too complexity to handle a relatively rare occurrence.  Closing." A **cost/benefit rejection, not a quality one** — code-reviewer had approved on the merits (including independently verifying the version-driven-service fix), implementation was verified against a real Docker daemon throughout. Both directions from the original ticket are now closed: Option 1 (auto-rollback, what got built) rejected on standing-complexity-vs-frequency grounds; Option 2 (health-gated cutover) was already ruled out at triage as materially larger. **Do not reopen or propose a slimmer variant unless lucas42 asks** — if this outage class recurs often enough to undermine "relatively rare", this ticket is the prior art to reopen, but that's a future trigger, not something to pre-empt. lucas42/lucos_deploy_orb#193 (version-resolution fix, `--points-at HEAD`) is unaffected and is now the *only* surviving lever for "re-run the last-green pipeline" as an emergency recovery path, since rollback is off the table — still open, Ready, High, mine, not yet dispatched.

**Lesson for scoping future infra proposals**: a mechanism can be spec-correct, reviewed, and verified, and still be rejected purely on "the standing complexity isn't worth it for how rarely this fires" — that's a legitimate, orthogonal axis from implementation quality, and worth weighing explicitly (frequency × blast-radius vs. ongoing maintenance surface) before investing in an elaborate mechanism next time, not just after the fact.
