**`Pipfile.lock`'s `_meta.hash.sha256` is a pure function of `Pipfile`, and pipenv `2026.4.0` began PEP 503-canonicalising package names — lowercase, `_`/`.` → `-` — before hashing.** Older pipenv (Dependabot's) does not. ⇒ **the two generations agree on any Pipfile whose package names are already canonical, and disagree ONLY where one is not.** So the skew is removable, not merely manageable: canonicalise the names and both compute the same value (which equals what the NEW pipenv already computes for the file as-is).

Measured 2026-08-26 against `lucos_backups/src/Pipfile`, unmodified, one file, six interpreters:

| pipenv | hash |
|---|---|
| 2026.2.1, 2026.2.2 | `15e6bab1…` ← what Dependabot writes |
| 2026.4.0, 2026.6.2, 2026.7.1, 2026.8.0 | `9319c363…` ← what our pinned image expects |

It is independent of Pipfile *content* but NOT of *naming* — a distinction I originally drew too coarsely and then reasoned from. Adding `idna = "*"` gives `674533b2…` vs `4fbb021a…`, still two answers, so "pin the dep so Dependabot's diff touches the Pipfile" does **not** fix it. Canonicalising the names does.

⚠️**Partial canonicalisation does not work.** `lucos_eolas` has two non-canonical names — `PyJWT` (case) and `lucos_loganne_pythonclient` (separators). Fixing only `PyJWT`: old `fd8f86ae…` vs new `f231f27d…`, still disagreeing. Fixing both: `f231f27d…` under both. **Grepping for mixed case alone half-fixes a repo and it fails on the next Dependabot PR.**

⚠️**Repo states differ, and rollout order depends on it.** `lucos_backups`' lock was regenerated by lucas42/lucos_backups#394 so it already carries the NEW hash ⇒ canonicalising is a Pipfile-only edit, no lock change (that is why lucas42/lucos_backups#404 is one line). `lucos_contacts`/`lucos_eolas` locks still carry OLD hashes ⇒ canonicalising moves the expected value and the lock then matches NEITHER until rewritten. Self-heals on the next Dependabot bump (that is what `old(canonical) == new(canonical)` means), but not instantly. **Per repo: canonicalise → let one bump land → then enable `--deploy`.** Enabling first reds CI on the first build.

**Why:** Dependabot's vendored pipenv predates 2026.4.0. Any repo whose Dockerfile runs `pipenv install --deploy` with a newer pinned pipenv will reject every Dependabot-authored lockfile, deterministically — the hash is a function of a file that did not change, so `@dependabot recreate` and CI re-runs reproduce it byte-for-byte. Confirmed on lucas42/lucos_backups#403 (blocked lucas42/lucos_backups#399 then #401, same `idna` 3.18→3.19 bump, identical hash pair).

**How to apply:**

1. **Do not read a `_meta.hash` mismatch as lockfile drift.** Classify it first: compute the Pipfile's hash under an old pipenv (≤2026.2.2) and a new one (≥2026.4.0). Three buckets — matches-new, matches-old, matches-neither. Only **matches-neither** is real drift.
2. Estate classification, 2026-08-26 (8 live repos with `pipenv install` in a Dockerfile): 6 matches-new (backups, media_weightings, media_import, contacts_googlesync_import, creds/configy_sync, arachne/ingestor), **2 matches-old — `lucos_contacts` (`app/Pipfile`), `lucos_eolas` (`app/Pipfile`)**, and **0 matches-neither**. That reproduces the architect's 08-17 "3 mismatched / 5 in sync" exactly (backups since fixed by lucas42/lucos_backups#394) and shows the whole estate finding was version skew, never drift.
3. ⚠️**Scope the claim.** "The `_meta.hash` mismatch is version skew" is a statement about that metadata field only. It does **not** establish that each lock's resolved package set satisfies its Pipfile constraints — a different measurement, and arguably the one the convention actually wants.
4. **Blocker for lucas42/lucos_repos#488** (estate-wide `--deploy` rollout): rolling it out does two things, not one — it enforces the lockfile *and* stops Dependabot landing any Python update in those repos. On `lucos_contacts`/`lucos_eolas` it reds CI on the first build, before any bump.

**API gotcha:** pipenv **2026.8.0 renamed the method** — `project.pipfile.calculate_hash()`, not `project.calculate_pipfile_hash()`. My first 2026.8.0 probe returned blank because of the `AttributeError`, which reads exactly like "disagrees with everything". Empty output is unknown, not data — see [[feedback_treat_empty_tool_output_as_unknown]].

## ⚠️ How I missed the fix while holding it (2026-08-26)

Brute-forcing candidate Pipfile edits for the one that produced Dependabot's `15e6bab1…`, I tested `pyjwt` lowercased, got `9319c363…`, logged `no: pyjwt lowercased`, and moved on. **That was the answer.** It didn't match because I was asking *"which Pipfile did Dependabot hash?"* — searching for the broken input — when the useful question was *"is there a Pipfile both versions agree on?"*, searching for the fix. `lucos-architect` asked the second question and found it in one step.

**How to apply:** when two tools disagree about a derived value, brute-forcing toward *the other side's* answer finds the cause; brute-forcing toward *agreement* finds the remedy. Run both searches over the same candidate set — it is the same experiment, read two ways, and the second one is the one that ships. Also: a negative result logged against the wrong target is not a negative result.

**Related correction:** "Dependabot recreate is deterministic, don't bother" (my call on lucas42/lucos_backups#401) is correct **only while inputs are unchanged** — a precondition I did not state. A Pipfile canonicalisation IS an input change, so recreate becomes legitimate immediately after lucas42/lucos_backups#404 lands. State the precondition whenever quoting the determinism rule.
