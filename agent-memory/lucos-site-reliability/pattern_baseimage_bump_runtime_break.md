**Red `main` pipeline right after an auto-merged Dependabot base-image bump = a RUNTIME/deploy failure, not a build failure.** `apk add`/package installs succeed at build; the breakage only surfaces when the daemon starts at deploy. So the bump passes the build-gated auto-merge and ships a latent runtime break.

**Diagnostic order:** workflow → jobs. If `lucos/build` = success and `lucos/deploy-<host>` = failed, it's runtime. Read the deploy step log (it shows the healthcheck/container failing), then SSH the host and read the *container* logs for the real fatal error. Don't reason from the build.

**Confirmed instance (2026-06-11, lucos_mail):** Dependabot #58 bumped `postfix/Dockerfile` `alpine:3.21.1 → 3.24.0`. Alpine 3.22+ ships **Dovecot 2.4**, which requires `dovecot_config_version` as the FIRST setting in `dovecot.conf` (`doveconf: Fatal: … The first setting must be dovecot_config_version`). Old config → dovecot crash-loops → `lucos_mail_smtp` healthcheck (`nc -z 127.0.0.1 25`) fails → mail down ~14 min. Restored by rerunning last-green pipeline (#146) then pinning alpine back (PR #59). Fix-forward = Dovecot 2.4 config migration (lucos_mail#60). Incident: `lucos/docs/incidents/2026-06-11-mail-alpine-dovecot24-outage.md`.

**Restore playbook for a base-bump outage:** (1) cancel queued reruns of the broken pipeline (`POST /api/v2/workflow/{id}/cancel`) so they stop redeploying the broken image — but first verify you're not orphaning the estate-wide avalon deploy lock (check Loganne: are other avalon deploys still landing?). (2) Restore by rerunning the last-GREEN pipeline (`POST /api/v2/workflow/{id}/rerun` `{"from_failed":false}`) — clean redeploy via the normal path. **Don't hand-roll the container** (no persistent compose on hosts; stateful volumes like mail-data risk loss). (3) Pin the base back via a one-line PR for durable green main. (4) File fix-forward issue + incident report.

**Recurrence trap:** repos with `dependabot-auto-merge.yml` will RE-OPEN and RE-MERGE the same base bump on the next daily run → re-break on a timer. The pin alone doesn't hold.

**The durable fix is a CI TEST JOB, not a Dependabot ignore and not "gate on deploy"** (lucas42's framing, 2026-06-11; he reframed my initial take). The real gap: the repo had no test that *starts the stack*, so nothing between merge and prod ran the daemon. A test that boots the stack fails in CI on the broken bump and **blocks the auto-merge outright** — cleaner than special-casing deploy-gating, and it removes the recurrence risk without any ignore. So: propose/await a stack-startup test (lucos_mail#61) as the fix-forward. A temporary `ignore` (PR #62, `alpine >= 3.22` on the `/postfix` updater only) is a *possible* belt-and-braces stopgap; its disposition is the owner's call (on this incident, supervised repo → left to lucas42 to approve=land or close=rely on the test job; aligns with his "let bumps flow, prefer no ignores" lean). Don't lead with "auto-merge should gate on deploy" — lead with "add a test that asserts the stack comes up." PROCESS LESSON: team-lead sent contradictory steers as info arrived (close→keep→close→open) and I toggled #62 each time (close+delete-branch ↔ reopen-restore-branch), which was churn — and one of their steers was based on a stale view of the PR's state (they thought it open when I'd re-closed it; I corrected that). Next time: wait for a *definitive* instruction before re-opening a PR you've closed, and when a steer assumes a state, verify the actual state first. Mechanic that made it recoverable: reopen-at-same-commit (recreate the deleted branch ref → old head SHA, then PATCH state=open) preserves the reviewer approval + green CI.

**Resolution status (2026-06-11):** lucos_mail#63 MERGED — added a `ci/circleci: test` job that builds smtp, starts the container with the `nc -z 25` healthcheck, and exits 1 if it doesn't go healthy. It's a REQUIRED check on main (branch protection: required = `ci/circleci: build` + `ci/circleci: test`). I verified the guard end-to-end: pushed a throwaway branch with `alpine:3.24.0`, the `test` job failed with the exact incident error (`doveconf: Fatal: … dovecot_config_version`), so the bad bump now dies at CI and can't auto-merge (auto-merge can't bypass a failing required check). #60 (Dovecot 2.4 migration) still open to eventually take the alpine upgrade.

**Reusable technique — verify a CI guard catches a bad change WITHOUT prod risk:** push a throwaway branch containing the bad change and watch the relevant CI job. Safe **only if the deploy job is gated to `main`-only** — CHECK `.circleci/config.yml` workflow `filters: branches: only: [main]` first; if deploy runs on branches, don't (it'd deploy the break). No PR needed (CircleCI builds all branches) → zero merge/auto-merge surface. Delete the branch after.

**⚠️ CRITICAL AMENDMENT (2026-07-31, lucos_media_metadata_manager) — the "red main" tell is NOT reliable.** The title of this pattern says red main + service down; that's only true when the break stops the container. `php:8.5.8-apache-trixie → 8.6.0alpha2-apache-trixie` (dependabot, classified `version-update:semver-minor`, auto-merged) shipped an image with **no `mbstring` extension** (8.5.8 bundles it, the alpha doesn't). `src/views/field.php:12` calls `mb_strlen()` on every rendered field → `Uncaught Error: Call to undefined function mb_strlen()` → bare 500 on every album/collection/track page. But: build green, deploy green, container **healthy**, monitoring **55/55 green**, `/_info` 200 throughout — because `/_info` only probed the *downstream* API and shares no code with the render path. Broken 07:46→14:15 UTC (~6.5h); first user-visible 500 not until 13:44 (nobody browsed in between), found by a user, never by a machine. **So: after any base-image bump, "main is green and the container is healthy" is NOT evidence the service works.** Diagnose via container logs + `docker exec <c> php -m` / equivalent, and compare against the previous image (`docker run --rm --entrypoint php <repo>:<prev-tag> -m`) — that comparison is the decisive one-liner. Incident: `lucos/docs/incidents/2026-07-31-media-metadata-manager-php-alpha-mbstring.md`. Restore PR lucos_media_metadata_manager#386 (revert + CI grep rejecting alpha/beta/rc tags).

**Estate defence inventory (2026-07-31) — 4 repos, 4 different mechanisms, NO convention:** lucos_media_import = dependabot `ignore` on python pre-releases (`*.pre.a`/`*.pre.b`/`*.pre.rc*`, ref lucos_backups#186, comment admits it may fail silently); lucos_mail#61 = CI job booting the stack; **lucos_eolas = `FROM app AS test` Dockerfile stage + `docker compose --profile test up test --build` — the best pattern, tests run in the shipped image by construction**; lucos_media_metadata_manager = CI grep rejecting pre-release tags. Everything else has nothing. Estate decision ticket: **lucos#273** (open). **Don't propose a blanket estate-wide pre-release ban** — the mail outage was a *stable* alpine bump so a ban wouldn't have caught it, and the estate has deliberately run pre-release python bases. The general fix is "test in the shipped image"; pre-release blocking is the cheap narrow stopgap.

**⚠️ AMENDMENT 2 (2026-08-17, lucos_backups) — 4th instance, and it adds a LATENCY property the first three didn't have.** Dependabot bumped `python:3.14.6-alpine → python:3.15.0a2-alpine` (a CPython **alpha**, classified `version-update:semver-minor`, auto-merged 08-06). **Nothing broke for 11 days.** It detonated on 08-17 only when a *third party* published `charset_normalizer` 3.5.1, whose `cp315` wheel is compiled against a later 3.15 pre-release with a wider C-API type-slot table → `SystemError: module charset_normalizer.cd uses unknown slot ID 84` on import of `requests`. Crash-loop, 877 restarts, backup service down **15h24m**. So: **the bump and the break can be weeks apart, and the triggering commit can be unrelated** (here a `github/codeql-action` bump — see below). Any guard that relies on noticing breakage *near* the bump sees nothing. Incident: `lucos/docs/incidents/2026-08-17-backups-python-alpha-charset-normalizer.md`; fix PR lucos_backups#391.

**`rc` is materially SAFER than `a`/`b` — CPython freezes its ABI at release candidate.** Tested on avalon: `python:3.15.0rc1-alpine` + `charset_normalizer==3.5.1` → `IMPORT OK`; `python:3.15.0a2-alpine` + same wheel → the SystemError. So a convention that distinguishes by pre-release *stage* is defensible on evidence; don't lump `rc` with `a`/`b` without testing. (2026-08-17 estate sweep: 98 repos, 42 Dockerfiles, 3 pre-release — 2 survivors both on `rc1` and both unexposed.)

**⚠️ THE RESTORE PLAYBOOK ABOVE (line "Restore by rerunning the last-GREEN pipeline") FAILED HERE — verify before relying on it.** Re-running `deploy-avalon` from the last-green pipeline redeployed the **broken** image: the orb's "Determine deployed version from git tags" step resolves the **newest tag**, not the tag at that pipeline's own commit. The step prints `Deploying version: X` in plain text — **read that line before assuming a rerun is a rollback.** It printed `1.4.33` (broken) when I wanted `1.4.31`. It reportedly worked on lucos_mail 2026-06-11, so this may be repo- or orb-version-dependent; treat "rerun = rollback" as a claim to check, not a fact. Also: with deploy driven over `DOCKER_HOST=ssh`, **there is no compose project dir on the host** (`com.docker.compose.project.working_dir` = `/home/circleci/project`), so `docker compose restart` on avalon is not available either. On this repo, fix-forward was the only path.

**A failed deploy leaves the service BROKEN, not unchanged.** `docker compose up` recreates the container and *then* waits on the healthcheck; when it never passes, the step fails but the previously-working container is already gone. Red CI ≠ "prod untouched".

**Check the ARTEFACT, not the commit log.** lucos_backups' `RUN pipenv install` re-resolves and **ignores `Pipfile.lock`** (image 1.4.32 ships lock `==3.4.9` + installed **3.5.1**). So the commit history pointed convincingly at the charset-normalizer lockfile PR, and reverting it would have been a no-op. One command settles it: `docker run --rm --entrypoint sh <img> -c 'cat Pipfile.lock | …; ls .../site-packages/ | grep <pkg>'`. Filed lucos_backups#392 (`pipenv install --deploy`).

**⚠️ THE lucos_media_metadata_manager PRE-RELEASE GUARD DOES NOT MATCH PYTHON TAGS — verified 2026-08-17.** Its regex `(alpha|beta|[-.]rc[0-9])` only catches the **verbose** spelling PHP uses. Tested: `php:8.6.0alpha2-apache-trixie` BLOCKED, but `python:3.15.0a2-alpine`, `3.15.0b2-alpine` and `3.15.0rc1-alpine` **all ALLOWED**. Python uses PEP 440's compact form. So "just roll out the existing guard estate-wide" is NOT a sufficient answer — it would have looked like protection and let the tag that caused the 15h backups outage straight through. Corrected pattern now live in `lucos_backups/.circleci/config.yml` (PR lucos_backups#394, deployed 1.4.35), validated 7/7 pre-release blocked + 13/13 legit allowed: `^FROM [^ ]*:[^ ]*(alpha|beta|[0-9](a|b|rc)[-._]?[0-9]|[-._]rc[-._]?[0-9])`. Known false-positive: a version-like `1b2` substring (e.g. `myimg:sha-1b2c3d`) — accepted, since a loud failed build beats a silent miss.

**Two guards, two moments — don't treat them as alternatives.** A *preventive* static tag check blocks the bump before the trap is armed; a *detective* test-in-shipped-image catches an artefact that won't run whatever the cause. On the 2026-08-17 incident the preventive half would have stopped the 08-06 bump, while the detective half would NOT have failed on 08-06 (nothing was broken for 11 more days) but blocked the 08-17 PR that detonated it. ⚠️Also: a detective repro is **time-dependent** — it works only while PyPI still serves the breaking wheel, and decays silently when upstream moves on. A *preventive* static check is deterministic forever. (An impossible test is caught by the first person who tries it; a test that quietly stops testing has no discovery path — `lucos-architect`, 2026-08-17.)

**Monitoring gap still open:** even with the CI test job, runtime **monitoring has NO smtp/port-25 probe** — lucos_mail checks are tls/fetch-info/circleci/apache (docs-side). A mail outage from a *non-bump* cause would still be invisible to monitoring except as a red `circleci`. The CI test guards the bump path; a synthetic-mail check would guard the runtime path — weigh vs hygiene/config cost before building.
