**mocha 11→12: bin entry point renamed + module type flipped.** mocha 12.0.0 renamed its CLI entry from `node_modules/mocha/bin/mocha` (no extension) to `node_modules/mocha/bin/mocha.js`, and switched that package from `"type": "commonjs"` to `"type": "module"`. A test script invoking node directly (`node --expose-gc --input-type=module ... node_modules/mocha/bin/mocha tests`, used to pass Node-only flags like `--expose-gc` that npx/mocha's own CLI can't forward) breaks two ways: the old path no longer resolves, AND Node's ESM loader throws `ERR_INPUT_TYPE_NOT_ALLOWED` for `--input-type=module` once the entry file itself resolves as an ES module (this only "worked" under mocha 11 because that entry loaded via the CommonJS loader, which never consults the flag). **Fix:** update the path to `bin/mocha.js` AND drop `--input-type=module` — it was never doing anything useful for a real file entry (the project's own package.json `type` field governs how its own test files are parsed regardless). Fixed in lucos_media_seinn PR #617.

**Stale `minimatch` override incompatible with newer transitive deps.** A global `"minimatch": "^X"` override added for a past CVE fix can go stale when some other dependency in the same bump group (e.g. `test-exclude`) needs a newer minimatch major with a different export shape (`minimatch is not a function` when the old CJS-function-export version collides with code expecting the newer named-export shape, roughly the v5/v7 → v9/v10 transition). **Fix:** check the GitHub Security Advisory for the CVE that motivated the original pin (`curl https://api.github.com/advisories/<GHSA-id>` — lists `vulnerable_version_range`/`first_patched_version` per major line) and bump the override to the newest major's patched version, not just the next patch within the old major. Verify via `npm view <pkg>@<version> dependencies` what minimatch range consumers actually need. Fixed in lucos_notes PR #515, same failure class as lucos_media_seinn#462 (that fix removed the override entirely rather than bumping it — either is valid depending on whether the CVE fix is still needed).

**General approach for "Dependabot PR failing" REQUEST_CHANGES from code-reviewer:** reproduce locally in a git worktree of the PR branch (`git worktree add`, don't touch the shared clone), `npm install` (restore package-lock.json first if you experimentally deleted it — regenerating from scratch pulls in unrelated version drift beyond the PR's intended bump), then bisect the actual failing command by hand (don't assume the code-reviewer's stack trace pinpoints the true root cause — trace it yourself with `npm view <pkg> dependencies`, reading the actual installed file content in `node_modules`, etc.).
