**lucos_worlds** — private worldbuilding system for TTRPGs (originating brief: lucas42/lucos#248).

**Decision (lucas42, 2026-07-07): ADOPT BookStack.** Not self-build. Single-user (lucas42).
- **Why adopt over self-build:** requirements collapsed to something small (single user, 3 fixed types, wikilinks deferrable, per-item single image) → adopt cheaper. BookStack chosen over kanka/Outline/Wiki.js: MIT licence (clean), **native OIDC SSO** (clean aithne integration, no fork), Book→Page hierarchy fits worlds→items. The tension: kanka has the typed model but own-auth; SSO wikis have auth but no typed model — BookStack + types-as-tags was the trade.
- **Model mapping:** world→Book, item→Page, type→tag (`type=pc|npc|place`); Place hierarchy = informal content convention, NOT first-class types. Types are a soft (unenforced) tag convention.
- **Deploy shape:** thin wrapper image `lucas42/lucos_worlds_web` FROM pinned upstream BookStack + MariaDB (new DB engine in estate). Two stateful volumes (DB + file storage). Fantasy CSS version-controlled in repo (BookStack Custom HTML Head Content verified; file-based `APP_THEME` theme system to confirm at setup).
- **Honest negatives recorded:** don't own the code (upgrade/security tracking via pinned tag + Dependabot; no CodeQL); MariaDB new engine; no native `/_info` (monitoring gap); aithne hard dep.

**BookStack extension-point taxonomy (2026-07-30, verified against v26.05.2 source).** Three tiers, and conflating them is what makes "no-fork" arguments go wrong:
1. **Sanctioned zero-drift hooks** — `layouts/parts/base-body-start.blade.php` and `base-body-end.blade.php` are **comment-only placeholder files**, upstream-described as "a placeholder template file provided as a convenience to users of the visual theme system". Overriding an intentionally-empty placeholder can NEVER conflict on upgrade (no upstream content to drift from). Same class as `functions.php` theme hooks. Use these first; they are NOT patches and don't engage ADR-0002.
2. **Theme override of a real view** — works, but you're maintaining a copy of an upstream blade file; drifts on upgrade.
3. **Dockerfile COPY patch of `/app/www`** — ADR-0002 territory, needs a pinning test. Only for things the theme system can't reach (the ES256 OIDC code).
CSS-only sits below all three: prefer it when achievable, because its failure mode on upgrade is "selector stops matching, behaviour reverts to stock" — graceful, no breakage.

**Tablet/split-screen constraint (< `$bp-l` = 1000px).** BookStack's tri-layout collapses to **mutually exclusive** "Info"/"Content" mobile tabs: `.tri-layout-left > * {display:none}`, and `.show-info` sets `.tri-layout-middle {display:none}`. Content OR info, never both — so anything in a sidebar (tags, the favourite ★ action) is unreachable while reading a page. Useful lever: grid rows are pre-assigned (`.tri-layout-left` = row 2, `.tri-layout-middle` = row 3), so un-hiding one sidebar block renders it **above** the content in normal flow with no DOM change. Also: the header **logo is an unconditional `<a href="/">`** outside all `hide-*` wrappers, so "/" is always one tap on narrow screens — which makes Application-Homepage-as-board a zero-code navigation win. Keyboard shortcuts (incl. `favourite`, `favourites_view`) are useless here — lucas42 uses this on a **split-screen tablet**, so any design leaning on keybindings is wrong for the real usage.

**Session-bookmarking design — RESOLVED 2026-07-30 (lucas42's West Marches use case).** **lucas42 is a PLAYER in these sessions, not the DM** — he learns the cast only on arrival, with no laptop. That single fact is the binding constraint: **any design requiring advance preparation is dead**, and on-the-fly capture on the tablet is the whole requirement. (If he ever DMs, he'd pack a laptop and the calculus changes.)
Options assessed: **Favourites** — per-user, no page revision, and NOT audit-logged (`ActivityType.php` has no favourite entry), so it leaves zero trace in world history, which is exactly the "not lasting" property wanted; tags+search **rejected** (writes a revision per page AND overloads the ADR-0001 `type=` convention with ephemeral scheduling state — rejected on *modelling* grounds, not effort); Recently Viewed (uncontrollable); bookshelves (books only, not pages). **Favourites is the answer.** Its `/favourites` list is ordered by lifetime **view count** (`QueryTopFavourites` → `orderBy('views.views','desc')`) and paginates at 20, so fresh stars sink — mitigated by clearing the set each session (#59) rather than by a pruning discipline.
**Superseded:** I first recommended a "Tonight" page as Application Homepage (revision history = free session log). Wrong for a *player* — dead on arrival with no laptop. **I'd ranked options for a user I imagined rather than asking how he actually uses the system** — and earlier in the same thread I'd ranked Favourites first on the strength of two keybindings that don't exist on a tablet. Ask for the usage context (device, role, when they find out what they need) *before* ranking options. See [[feedback-ask-usage-context-before-ranking-options]].

**Dark mode — #42's "can't be disabled" claim REVERSED (2026-07-30, assessment on #61).** Verified against BookStack v26.05.3 source:
- **#61 root cause:** `resources/sass/_text.scss:49` — `h1…h6 { lightDark(color, #222, #BBB) }`. Theme forces the reading card to parchment `#F7F0DC` in both modes, so dark-mode headings are `#BBB` on cream = **1.69:1** (measured darkest pixel `rgb(189,173,155)` = that blended with the card noise, 1.92:1). `:root.dark-mode body { color:#3a2a1a }` doesn't reach them — inherited colour loses to upstream's direct `h1…h6` rule. The ticket's "computed style says `#222` in both modes" is **inconsistent with the source** (should be `#BBB`) — a mismeasurement, not a rendering mystery.
- **Structural cause, not a one-off:** #42 forces *some backgrounds* light in dark mode; upstream flips *all* foregrounds light (47 `lightDark(color,…)` decls). Most are safe because they flip bg+fg together (code `#2B2B2B`, blockquote/tables `#333`, callouts) — headings are the one card element with a foreground flip and no background of its own. Links in dark mode = BookStack blue `#206ea7` on parchment = 4.79:1 (passes AA, off-brand, narrowest margin).
- **Dark mode CAN be removed:** `resources/views/common/dark-mode-toggle.blade.php` is one self-contained partial included from all 5 sites (`layouts/parts/header-user-menu.blade.php` + 4 home views); `ThemeViews.php:39` does `finder->prependLocation(theme_path())`, so an **empty** theme override kills all 5. No patch, ADR-0002 not engaged; benign upgrade failure (toggle just reappears). **No `prefers-color-scheme` anywhere in BookStack** — dark mode is opt-in via that one button only; single write path is `UserPreferencesController::toggleDarkMode()` / `PATCH /preferences/toggle-dark-mode`.
- **Must ship with a preference clear:** persisted at `settings` key `user:<id>:dark-mode-enabled`; use `SettingService::remove(...)` in a `custom-cont-init.d/40-…` `artisan tinker` script (pattern = `20-set-branding.sh`). Without it, removing the toggle strands the user in dark mode.
- **Not a hard lock:** theme routes can't shadow core ones — `RouteServiceProvider::mapWebRoutes()` requires `routes/web.php` *before* dispatching `ROUTES_REGISTER_WEB(_AUTH)`, and Laravel takes the first match. A real lock needs a patch; not worth it single-user.
- **Unlock if removed:** drops 6 mode-scoped blocks + ~25-line header comment from `custom.css`, and dissolves the `--color-primary`/`--color-link` light-mode-only compromise (brown becomes unconditional → mobile tab bar, back-to-top, favourite pill go on-brand). Gotcha for the tidy-up: emptied partial leaves an empty `<li>`/`.icon-list`; `li:empty` will NOT match (whitespace text node) — use `li:not(:has(*))`.
- **Recommended Option B (remove the toggle)**; Option A (re-assert `#222` on lightened surfaces, ~4 lines, needs surface enumeration) is the fallback. Awaiting lucas42.

**BookStack internals verified against `lscr.io/linuxserver/bookstack:26.05.2` (2026-08-06)** — expensive to re-derive, applies to any future worlds design:
- **Three editors**: `wysiwyg` (TinyMCE, legacy), `wysiwyg2024` (Lexical, current), `markdown`. `PageEditorType::getSystemDefault()` falls back to **TinyMCE**; but `forPage($page) ?: getSystemDefault()` means **a page's stored editor wins** — switching the default never touches existing pages. lucas42 switched to Lexical 2026-08-06.
- **Lexical registers a CLOSED set of ~17 node types** (Callout, Heading, Quote, List, Table, Caption, Image, HorizontalRule, Details, CodeBlock, Diagram, Media, Paragraph, Link) with **no arbitrary-element node** → any custom `<div class="…">` is discarded on save. **Never design worlds content on custom HTML wrappers.**
- **`CalloutNode::createDOM()` returns a `<p>`** — a callout is ONE paragraph, applied via `$toggleSelectionBlockNodeType` like Blockquote. It **cannot contain** a table/heading/details. Emits `class="callout {info|success|warning|danger}"` — the only native, stable CSS hook available (no way to add a custom class via the editor UI).
- **`DetailsNode` IS a real container** — `<details>` + `<summary>`, holds block content, has an `__id` but no class hook. Buttons: "Insert collapsible block", "Edit label", "Toggle open/closed", "Unwrap".
- **Transclusion exists**: `{{@<pageId>#<sectionId>}}`, resolved by `PageContent::render()`, nested ≤3 deep, tags generated by the select-text `pointer.ts` widget. References pages by **numeric ID** (rename-safe, but opaque in source; source-page restructure silently renders blank).
- **`HasDefaultTemplateInterface` implemented by `Book` and `Chapter`** (not tags) — the reason chapters unlock cheap templating. Plus `PageTemplateController` (saved templates) and a page **copy** route.
- **Export** at page/chapter/book level → pdf/html/markdown/plaintext. Only offline mitigation (BookStack is not a PWA).
- **Page URLs are `/books/{bookSlug}/page/{pageSlug}`** — chapter slug absent, so moving a page between chapters breaks no links.
- **`PageContent::getNavigation()` builds the sidebar from heading elements anywhere in the rendered HTML** — headings nested inside a details/callout still pollute page nav.
- **No hover-preview/tooltip component exists** (enumerated all of `resources/js/components`); `popup.js`/`entity-selector-popup.ts` are dialogs, `pointer.ts` is select-text-to-link.
