**Verified live (2026-08-26, lucas42/lucos_agent#78):** with zero `Circle-Token`/auth header, `GET /api/v1.1/project/github/lucas42/{repo}?limit=1` returns full build metadata, and following a build's step `output_url` (presigned, self-authorizing) returns the **actual step stdout/stderr** — I fetched a real job's log this way and got back its real output. Confirmed `oss: true` on every repo checked (`lucos_agent`, `lucos_creds`, `lucos_monitoring`, `lucos_deploy_orb`) — this is estate-wide, not a one-off misconfiguration.

**What this means for any "should we put a secret in CircleCI" question:** the only in-band protection against a provisioned secret leaking is CircleCI's exact-string value masking, which is well-known to be incomplete — it catches the raw value verbatim, not a re-encoded/partial/differently-formatted echo of it. Any future one-line regression (a `set -x`, a debug print, an exception path that embeds more than intended) is the whole distance between "working CI step" and permanent, public, unauthenticated disclosure. No login, no org membership, no GitHub access required to read it — worse than "internal" by the estate's own no-internal-network standard ([[risk-prompt-injection-and-ci-logs]] is the sibling finding, about untrusted *input* via CI logs; this is about secret *output* via CI logs).

**Prior acknowledgment — already estate status quo, don't re-litigate per-ticket:** `LUCOS_DEPLOY_ENV_BASE64` and `KEY_LUCOS_MONITORING` are live CircleCI project env vars on `lucos_creds` (confirmed via API, values masked in the listing) — `lucos_creds` is `oss: true` too, and `LUCOS_DEPLOY_ENV_BASE64` is materially more sensitive than most credentials that would ever come up (see [[lucos-creds-scoped-key-permissions]]). So "masking-only protection on a public-log OSS CircleCI project" is already accepted for higher-stakes secrets than most future asks. Don't raise the general exposure model as a novel blocker on a per-repo ticket — it's a settled estate-wide architecture choice; if it needs revisiting that's its own cross-cutting ticket, not something to back into via one repo's CI-secrets ask.

**The fork-PR vector is separately closed, checked the same way**: `feature_flags.build-fork-prs: false` and `forks-receive-secret-env-vars: false` confirmed on all four repos checked. So external/malicious PRs can't reach CircleCI secrets regardless of the masking question above — that vector doesn't need re-checking per-repo unless a repo's settings differ.

**What still varies per-ask, and what I actually recommend:** whether the *specific* credential being proposed is disposable/CI-scoped, or is someone's live operating credential. For lucos_agent#78 (`LUCOS_ARCHITECT_AITHNE_CLIENT_SECRET` — the real credential the interactive `lucos-architect` agent uses day-to-day), recommended minting a **dedicated CI-only aithne client** (e.g. `lucos-agent-ci-smoketest`, scope-matched, nothing else depending on it) rather than copying the live value in — aithne's per-principal model supports this natively (one more `client_id`/`secret` pair, not new machinery). That way a masking-bypass leak costs "rotate a disposable token," not "emergency-rotate a working agent's actual credential." **Apply this same split (dedicated-vs-live) as the live question on any future "provision X into CircleCI" ask — the public-logs fact above is settled, but which specific credential value goes in is not.**

**Related:** an unused `circleci-agents` CircleCI context exists org-wide (created earlier, currently empty) — plausibly intended for exactly this class of credential; worth using instead of a raw project env var if the pattern is likely to recur across agent-related repos.

**UPDATE 2026-08-27 — researched: no CircleCI setting/plan makes build logs private for a project linked to a public repo.** Structural product limitation, not a missed config — CircleCI's own OSS docs state it directly, and the "Free and Open Source" toggle (the `oss` API flag) only gates *unauthenticated* visibility; per CircleCI's own community guidance, any authenticated CircleCI user (not org-scoped) can still see logs regardless. Open CircleCI feature request for exactly this exists since ≥2023, no official response. **So there's no middle option** — the choice is genuinely binary: accept the current exposure for what's inside `LUCOS_DEPLOY_ENV_BASE64`, or change what's in it / how the self-deploy mechanism works. Posted on lucas42/lucos#291.

**UPDATE 2026-08-26 — filed as its own ticket, lucas42/lucos#291 (Owner me, Medium).** Ran the lightweight historical-leak check first: read the current pipeline code path for `LUCOS_DEPLOY_ENV_BASE64` (decodes straight to a file, never echoed) and spot-checked 3 recent `lucos_creds` deploy job outputs — no leak found, only CircleCI's own built-in "Preparing environment variables" step lists the var names (no values, not even masked). Explicitly scoped that as 3 recent builds + current code, not exhaustive history. `KEY_LUCOS_CREDS` cited via its actual source doc (`lucos/docs/runbooks/update-lucos-creds-production.md`: "the master credential for the credential store itself"), not via my own memory framing.
