**Standing architectural gap, independent of any specific incident:** `lucos_creds`'s server (`server/src/storage.go`, `keys.go`) has two secrets that follow the same "generate on first boot if the file is absent" pattern (`getCreateBlockCipher` / `getCreateSshSigner`), but they are NOT equally rotatable:

- **`server_key`** (`/var/lib/creds_store/server_key`, the SSH host identity for `creds.l42.eu:2202`) — free to rotate. It authenticates the server to connecting clients only; it doesn't encrypt any stored data. Omit it from a restore/redeploy and the server mints a fresh one; clients just need a `known_hosts` update.
- **`data_key`** (`/var/lib/creds_store/data_key`, AES-256-GCM key encrypting every stored credential's `EncryptedValue` in the sqlite store) — **there is no rotation/migration tooling anywhere in the repo.** Deleting the file does not rotate the key; the server generates a fresh one and every existing encrypted row becomes permanently undecryptable (no decrypt-old/re-encrypt-new path exists). A real rotation requires new migration code that has never been written.

**How this surfaced:** avalon's disk failed (lucas42/lucos#294) and left custody unencrypted for OVH's disk swap (lucas42/lucos#296). The architect framed "restore the old creds keys vs. mint fresh ones" as one decision; I read the source before answering and found it's actually two decisions with very different costs. My assessment (posted https://github.com/lucas42/lucos/issues/296#issuecomment-5673068021): rotate `server_key` (free), treat `data_key` as a consciously-accepted risk for this restore, and file a proper follow-up to build the rotation tooling as standing debt — not something to build under incident pressure.

**How to apply:** any time a `lucos_creds`-adjacent decision talks about "rotating the creds keys" as a single action, check which of the two this actually means — the cost difference is the whole ballgame. Tracked as lucas42/lucos_creds#565.

**Pick-up guidance changed 2026-09-18 (team-lead, recorded on both #565 and #418): design #565 alongside #418's key-handling design, not before or independently of it.** #418's DR-escrow requirement (if `data_key` leaves the routine backup, it must stay reachable by lucas42 with avalon gone) changes where/how `data_key` is stored and obtained — exactly the surface #565's rotation procedure has to manipulate. Designing them separately produces two incoherent answers. Also: #565 is the remediation path if #418's aurora question resolves badly (a possibly-exposed key needs rotation, and #565 says no such code path exists) — not urgent today, but the aurora answer determines whether #565 becomes urgent. See [[feedback-cross-reference-coupled-tickets]] for the general habit this incident prompted.

**Related, more urgent finding (2026-09-18):** the rotation gap above is about *capability*; separately, the `data_key` + `creds.sqlite` co-location is **currently readable today**, rotation notwithstanding. Routine daily/monthly `lucos_backups` volume archives are created world-readable (644, no `umask`/`chmod` in `Volume.archiveLocally()`) — confirmed directly on xwing (`lucos-agent` could read `lucos_creds_store.*.tar.gz` without owner/group access, archives dated back to 2026-01-06). Filed as lucas42/lucos_backups#418.

**Severity revised same day, after `lucos-site-reliability` enumerated accounts:** on avalon/xwing/salvare, every account that can log in is already `sudo` or `docker`-group (root-equivalent per [[risk-lucos-agent-docker-group-root-equivalent]]), so the 644 mode grants nothing #102 doesn't already grant there — downgraded to Medium for those three hosts (real hygiene, not a live incremental exposure). **Aurora is the exception and still open**: confirmed via configy's `volumes.yaml` that `lucos_creds_store` has no `skip_backup_on_hosts`, so it backs up there too, and lucos-agent has zero access to aurora (different account model, QNAP/busybox) — no #102-style redundancy applies. Held at Critical pending lucas42 checking aurora's account list; neither security nor SRE can check it.

**Separately live, 2026-09-18 (lucas42/lucos#301 thread):** lucas42 rejected building a runbook around agents extracting `data_key` from backups mid-incident, and proposed instead a *deliberate* policy — `lucos-agent` gets standing group-read on backup-storing hosts. My assessment, given to `lucos-site-reliability` for a joint write-up: this resolves the process objection (deliberate vs stealthy access) but **must not be read as resolving #418** — "read access to backups" and "decrypt every production credential" are the same grant only because of the colocation above, so any such policy needs `lucos_creds_store` excluded (600 / separate ACL) until `data_key` is decoupled. Also: for `lucos-agent` specifically, none of this permission engineering matters at all while #102 stands — see that file's "concrete instantiation" note (including the correction that decoupling `data_key` from the *backup* only closes the backup-file vector, not the live-volume-mount one on avalon — that needs #102's own remedy).

**Resolved on lucas42/lucos_backups#418 (venue settled 2026-09-18, since lucas42 closed #301 himself and it's staying closed):** board Priority is **High while the aurora account question is open** (team-lead: briefly lowered to Medium on the three-host account-redundancy finding, then raised back to High within the hour once the aurora point landed — "severity hinges on an unknown fact" is what High should look like while that's true; drops back to Medium the moment lucas42 confirms aurora has no non-root-equivalent login account). My own severity call, Critical-pending-aurora, is a separate axis (impact-if-reached vs. board queue position) and stayed consistent throughout — track the *condition* here, not a specific number, since it moved twice in one hour and will move again once aurora is answered. Two durable constraints landed on that ticket regardless of where the number sits: (1) **sequencing** — #418's fix must land before or with any #102 remedy, never after, since narrowing #102 first would turn this from latent into live; (2) **DR escrow** — if `data_key` leaves the routine backup, it must stay recoverable by lucas42 with avalon gone (the 2026-09-14 rescue depended on the key being in the copies), so decoupling can't just mean "delete it from the tarball."
