lucas42/lucos#307 (2026-09-28, photos.l42.eu 9h14m outage follow-up): `registry-mirrors: ["https://docker.l42.eu"]` has never served any host daemon — `lucos_docker_mirror`'s nginx (`nginx.conf.template`) gates all of `location /` with `auth_basic`; dockerd sends no credentials to a configured mirror, so every host pull 401s and silently falls back to Docker Hub anonymously. CI authenticates fine (sends real basic-auth creds).

SRE proposed exempting host daemons from `auth_basic` via an IP allowlist (`satisfy any`). This went through two rounds of correction on lucas42/lucos#307 (both by me, both verified independently before posting, not just taken on trust) — worth keeping the full arc since each mistake was an easy one to make:

**Round 1 mistake:** I said the mirror's port is directly internet-reachable ("no host firewall"), citing `references/network-topology.md` without checking its date (2026-04-09, predates ADR-0007's enforcing default-deny firewall, live since 2026-06-08). Corrected after verifying against configy (`hosts.yaml` `firewall_enforce: true` on avalon; `systems.yaml` — `lucos_docker_mirror` has no `public_ports` entry) and empirically (`curl http://178.32.218.44:8038/v2/` times out; only `https://docker.l42.eu/v2/` via the router responds). **This part held up** — the mirror's port really is firewalled, `network-topology.md` was fixed (`35706414`) to reflect ADR-0007.

**Round 1 "fix" (also wrong):** having confirmed the router is the only path in, I concluded an IP-allowlist keyed on `X-Real-IP` (which `lucos_router`'s nginx sets from its own `$remote_addr`, overwriting any client-supplied value) would be sound, since the direct-port bypass that would let an attacker forge it doesn't exist.

**Round 2 correction (SRE caught it):** `X-Real-IP` is *not* trustworthy for IPv6 clients specifically. `lucos_router`'s `docker-compose.yml` declares no network / no `enable_ipv6` — its container is IPv4-only on the default bridge. Docker still publishes `80`/`443` on avalon's IPv6 address (dual-stack host), so `docker-proxy` terminates IPv6 arrivals and re-originates them to the container over IPv4 — nginx's own `$remote_addr` for an IPv6 client is *already* a fixed internal address before `X-Real-IP` is even set from it. SRE's router-log evidence confirmed this empirically (facebookexternalhit, ~23k Mozilla requests, remote `lucos_media_linuxplayer` instances — all logged as source `172.16.5.1`, across every domain the router serves, not just docker.l42.eu). Since host daemons reach the mirror over IPv6 too, they'd present the same collapsed address — an allowlist admitting them admits any IPv6 client on the internet. I verified the architectural mechanism (the compose file) independently before accepting this, not just SRE's word for it.

**Also undermined in round 2:** my "prefer credential-based (`docker login`), reusing what already works for CI" recommendation. SRE found `moby/moby#30880` — a **still-open upstream issue since 2017** — describing exactly this symptom: `docker login` credentials for a registry are honoured for a direct pull, but ignored when the same registry is used via `--registry-mirror`, producing the identical `no basic auth credentials` error. I read the issue directly. Nine years unresolved ⇒ dockerd fundamentally has no path to authenticate a mirror pull; the credential-based fix has no mechanism to hang off.

**Where this leaves it (as of 2026-09-28): neither sketched design for "make the mirror serve host daemons" is safe/viable.** Open design question for whoever picks up the separate ticket — possible avenues not yet evaluated: mutual TLS client certs (`/etc/docker/certs.d/<registry>/`, known-supported for *direct* registry auth, unverified for the mirror role), or an architecture that doesn't route host-daemon pulls through `registry-mirrors` at all. I asked to review whatever mechanism gets proposed before it ships, given two wrong "safe" answers in a row on this one.

**General lessons:**
1. Check reference-doc staleness against a relevant ADR before citing an architectural absolute (`git log -1 -- references/<file>` vs. the ADR date) — this is now a standing rule in the persona file (`agents/lucos-security.md`, "Resolve factual gaps" bullet).
2. **A corrected conclusion is not automatically a verified one.** The round-1 fix ("X-Real-IP is trustworthy") felt solid because it followed logically from a freshly-verified fact (port is firewalled) — but the reasoning chain had an unverified link (whether the router's own view of the client IP is itself trustworthy for *every* client, not just the ones that can't bypass the port). Fixing one wrong premise doesn't mean the new conclusion is safe to publish without checking its own premises just as hard as the one that just got caught.
